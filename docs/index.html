Ranking Content Pages for Human Refresh Review

A public-safe machine-learning study that compares a hand-written rule with learned ranking models, audits leakage, and turns validated scores into a transparent content action playbook.

Abstract

This project asks whether anonymized search-performance signals can help rank content pages for human refresh review. I compared a Week-4 rule baseline with Logistic Regression and Random Forest using a grouped client holdout and Precision@20 as the primary ranking metric. The initial Week-5 model comparison selected Logistic Regression, which achieved 80% Precision@20 versus 45% for the rule baseline, but a later audit found that several trailing-90-day features overlapped the retrospective outcome window. After restricting the analysis to pre-outcome measurements, the more defensible validation produced 65% Precision@20 for Logistic Regression, while the final Week-7 queue selected Random Forest at 70% Precision@20 on the same strict feature design. The result is a ranked, human-reviewed decision-support playbook rather than an automated or causal content-refresh system.

Introduction / Problem statement

Content teams often have more pages than they can review at once. A raw model score is not useful unless it helps a person answer a practical question: which pages should be inspected first, and why?

This capstone supports that decision by ranking anonymized pages according to observed decline risk, previous visibility, and estimated review effort. The intended user is a content strategist, SEO analyst, or editor. Every recommendation remains subject to human review.

Data

The analysis uses the public-safe FlyRank ML Internship starter slice in data/raw/content_refresh_anonymized.csv. It contains 30,000 anonymized page-level rows across 32 pseudonymous clients. This is a teaching slice derived from the wider FlyRank warehouse; the model in this capstone was not trained directly on all 79 million warehouse rows.

The retrospective outcome identifies whether a page was observed as declining. The strict validation design uses measurements from the preceding 30-day window to avoid using information from the latest 30-day outcome period.

Public-safety exclusions: client names, domains, URLs, private queries, credentials, raw exports, direct identifiers as model features, and label-derived fields were excluded.

Methodology

Label and features

The evaluation label is a retrospective decline indicator derived from trend_direction. The strict feature set uses only pre-outcome measurements:

previous 30-day impressions previous 30-day clicks previous 30-day sessions previous-window CTR sessions per 100 impressions measurement-availability flags

Baseline

The Week-4 rule required at least 300 impressions and a valid position. It prioritised pages that were at least 180 days stale, had CTR at least 20% below the median for their position bucket, or met both conditions.

Models and validation

Logistic Regression and Random Forest were compared. Clients were split as groups so that no client appeared in both training and testing. The random state was fixed at 42. Precision@20 was the primary metric because the operational task is to identify the first 20 pages for review; Precision@50, average precision, and ROC AUC were supporting metrics.

Leakage checks

The feature list excluded content_id, client_id, trend_direction, trend_pct, the derived label, baseline scores, action labels, and reason codes. The audit also tested a deliberately invalid trend_pct probe, which reached perfect metrics and confirmed that the harness detects answer-derived leakage. That probe was removed from all valid conclusions.

Limitations & honest framing

  • The label is retrospective and does not directly measure the causal effect of a future refresh.
  • The starter slice contains 30,000 pages across 32 pseudonymous clients, so external validity is limited.
  • The value score uses visibility as a proxy and is not a revenue or business-impact estimate.
  • Review effort is approximate and must be replaced by an editor’s real work estimate.
  • The model does not reveal or prove Google’s ranking algorithm.
  • Observed associations do not prove that staleness, CTR, or any other feature causes decline.
The output should be described as observed, measured, directional, and decision-support. It should not be described as automatic, causal, or production-ready.

Ranked recommendations

The final score combines model risk, previous-window visibility, and a lightweight effort estimate. Every row receives human-readable reason codes.

REFRESH_REVIEWHigh observed risk and stale content. Inspect accuracy, intent, structure, and outdated sections.
METADATA_REVIEWHigh observed risk, meaningful visibility, and CTR below the position reference. Review title and description alignment.
DIAGNOSE_FIRSTHigh observed risk with limited visibility. Check indexing, tracking, intent, and possible cannibalisation before editing.
MONITOR_AND_REVIEWMedium risk with meaningful value. Recheck in a later measurement window.
PROTECT_AND_MONITORLow risk with strong visibility. Avoid unnecessary edits and continue monitoring.
DATA_QUALITY_REVIEWInsufficient measurement history. Investigate data quality before drawing a performance conclusion.

What must not be automated

The system must not automatically publish, rewrite, delete, merge, prune, redirect, or change metadata. It must not expose private data, infer Google’s algorithm, or act solely on a model score.
